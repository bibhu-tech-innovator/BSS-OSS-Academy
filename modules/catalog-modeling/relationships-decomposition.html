Section 2.3

Relationships & Decomposition

How catalog entities relate to each other

Catalog entities do not exist in isolation. They are connected through a web of relationships that define how products, services, and resources interact. Understanding these relationships is essential for designing catalogs that correctly decompose orders and automate fulfilment.

Catalog Entity Relationships
Entities connect through structured relationships: references, realisations, and decompositions

Catalog Relationship Types

The TM Forum SID (Shared Information Data) model defines several relationship types that govern how catalog entities connect. Each relationship type has a specific purpose, direction, and set of rules.

Relationship Direction Purpose Example
Bundling Offering → Offering A commercial offering contains other offerings. Defines the bundle structure at the product catalog level. "Triple Play" bundle contains "Broadband 100" + "VoIP Basic" + "IPTV Starter"
Composition Spec → Sub-Spec A specification is composed of sub-specifications. Defines the structural hierarchy within a specification. "Ethernet Access Spec" is composed of "Physical Port Spec" + "VLAN Spec"
Dependency Spec → Spec One specification depends on another. The dependent entity cannot exist without the target. "VoIP Service Spec" depends on "Broadband Access Spec" for transport
Exclusion Spec → Spec Two specifications cannot be active simultaneously on the same customer or resource. "VLAN 100" and "VLAN 200" on the same port (exclusive VLAN pools)
Realisation Spec → Spec (cross-layer) A higher-layer entity is realised by a lower-layer entity. The core decomposition mechanism. "Product Spec" is realised by "CFS Spec"; "CFS Spec" is realised by "RFS Spec"
Decomposition Order → Sub-Orders An order decomposes into sub-orders across the commercial and technical boundary. Commercial Order splits into Service Orders, which split into Resource Orders
Resource Binding RFS → Resource An RFS instance is bound to a specific resource instance. Links the service to the network asset. "BNG Session RFS" is bound to "BNG-7 Interface 3" resource

Decomposition

Decomposition is the process of breaking down a higher-level entity into its constituent lower-level entities. In the catalog world, decomposition happens at multiple layers:

Order Decomposition

When a customer places an order for a product, the Commercial Order Management (COM) system decomposes it into one or more Service Orders. Each Service Order targets a specific CFS or RFS. The Service Order Management (SOM) system further decomposes Service Orders into Resource Orders that the ROM system executes against domain controllers.

Conditional Decomposition

Not all decompositions are fixed. Conditional decomposition rules determine which sub-entities are created based on the characteristics of the parent order:

  • Technology-based: FTTH vs DSL vs 5G FWA — each triggers a different set of RFS and resource requirements.
  • Geography-based: Urban vs rural may use different OLT types or backhaul configurations.
  • Segment-based: Residential vs business may trigger different SLA monitoring RFS instances.

Key insight: Conditional decomposition is what makes catalog-driven architecture powerful. Instead of hard-coding fulfilment logic, the catalog encodes the rules, and the orchestration engine interprets them at order time.

Decomposition at Runtime vs Design Time

Some decomposition happens at design time — the catalog defines the possible decompositions, the relationship types, and the rules. Other decomposition happens at runtime — when an order is placed, the orchestration engine evaluates the rules and creates the specific set of sub-orders, service instances, and resource allocations needed.

Key Takeaways

Key Takeaways

  • Catalog entities connect through seven key relationship types: Bundling, Composition, Dependency, Exclusion, Realisation, Decomposition, and Resource Binding.
  • Realisation is the cross-layer relationship that connects product → service → resource specifications.
  • Decomposition is the runtime process of breaking orders into sub-orders across the COM/SOM/ROM boundary.
  • Conditional decomposition rules allow the catalog to encode flexible fulfilment logic based on technology, geography, or segment.
  • The combination of relationship types and decomposition rules is what makes catalog-driven automation possible.
