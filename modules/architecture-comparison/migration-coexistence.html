Migration & Coexistence Patterns

Strangler fig, parallel run, and anti-corruption layer strategies

BSS/OSS transformation is never a greenfield exercise. Every operator has a legacy landscape that must continue running while the target architecture is built. This section covers the three essential migration patterns for BSS/OSS.

1. Strangler Fig Pattern

Named after the fig that grows around a host tree, the strangler fig pattern incrementally replaces legacy system functionality with new components. As each new component is proven, the corresponding legacy function is retired ("strangled").

Steps:

  1. Identify a bounded capability to replace (e.g., Product Catalog).
  2. Build the new component alongside the legacy system.
  3. Route new transactions to the new component; continue routing existing transactions to legacy.
  4. Migrate existing data from legacy to new.
  5. Cut over all traffic to the new component.
  6. Decommission the legacy function.

BSS/OSS application:

  • Extract Product Catalog from the legacy billing system to a standalone TMF Catalog component.
  • Replace legacy order management with a new ODA-compliant COM.
  • Introduce a new SOM without touching the existing COM (see Module 8.2 for the brownfield approach).

2. Parallel Run

In a parallel run, both the legacy system and the new system process the same transactions simultaneously. Outputs are compared to validate the new system's correctness before cutover.

AspectLegacy SystemNew System
Processes transactionsYes (primary)Yes (shadow)
Drives actual operationsYesNo (read-only / shadow mode)
Data comparisonBaselineCompared to baseline for validation
DurationThroughout parallel runUntil validation is complete

BSS/OSS application:

  • Run new billing system in parallel with legacy billing for one billing cycle to compare invoice outputs.
  • Shadow-mode order processing to validate SOM decomposition logic before cutover.
  • Parallel rating of usage records to validate the new charging engine.

3. Anti-Corruption Layer (ACL)

The ACL pattern prevents legacy system concepts, data models, and protocols from "leaking" into the new system. The ACL sits between the new system and the legacy system, translating requests and responses in both directions.

ACL responsibilities:

  • Protocol translation — Legacy SOAP/XML to modern REST/JSON.
  • Data model mapping — Legacy data model to SID-compliant model.
  • Behaviour adaptation — Legacy synchronous behaviour to asynchronous event-driven patterns.
  • Default handling — Provide sensible defaults for data that the legacy system does not capture.
  • Circuit breaking — Protect new system from legacy system failures.

Migration Pattern Selection Guide

SituationRecommended Pattern
Replacing a well-defined, bounded capability (e.g., Catalog)Strangler Fig
High-risk replacement where correctness is critical (e.g., Billing)Parallel Run + Strangler Fig
New system must coexist with legacy for extended periodAnti-Corruption Layer + Strangler Fig
Third-party integration where legacy cannot changeAnti-Corruption Layer
Complete platform replacement (big bang)Not recommended for BSS/OSS — too high risk

Common Pitfalls in BSS/OSS Migrations

  • Underestimating data migration complexity — Legacy billing systems often have 20+ years of data with inconsistent formats, missing references, and undocumented business rules.
  • Skipping the ACL — Direct integration between new and legacy creates a tightly coupled hybrid that is harder to decompose.
  • Parallel run without automated comparison — Manually comparing outputs does not scale.
  • Big bang cutover — The risk of revenue impact from a failed cutover is too high; always prefer incremental strangling.

Key Takeaway

The strangler fig pattern, with an anti-corruption layer to protect new components, is the most reliable approach for BSS/OSS transformation. Parallel runs should be used selectively for high-risk components (billing, rating). The key principle is: never replace a legacy system — grow a new system around it and strangle the old one incrementally, capability by capability, with each strangulation delivering independent business value.
