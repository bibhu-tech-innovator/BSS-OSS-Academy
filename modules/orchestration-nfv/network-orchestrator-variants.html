11.7 Network Orchestrator Variants & Specialised Domains

EMS, NMS, domain orchestrator, and SDN controller taxonomy

The OSS domain contains a spectrum of management and orchestration systems. Understanding the taxonomy — from EMS up to the cross-domain orchestrator — is essential for designing the orchestration layer of a modern telecom network. This section clarifies the different types of network control and management systems, their roles, and where they fit in the orchestration hierarchy.

EMS — Element Management System

An EMS manages a specific type or family of network elements from a single vendor. It provides:

  • FCAPS functions: Fault, Configuration, Accounting, Performance, Security management for the managed elements.
  • Vendor-specific abstraction: The EMS exposes a standardised interface (e.g., NETCONF/YANG, REST, CORBA) northbound while managing vendor-proprietary protocols southbound.
  • Element lifecycle: Discovery, provisioning, software upgrade, and decommissioning of individual network elements.

Examples: Nokia NFM-T (for transport), Ericsson ENM (for mobile), Huawei U2000. The EMS is the lowest level of management — it deals with individual devices or VNFs rather than end-to-end services.

NMS — Network Management System

An NMS sits above the EMS layer and provides multi-vendor, multi-technology network management. Unlike the EMS, which is element-centric, the NMS is network-centric — it manages the network as a whole rather than individual elements. Key functions include:

  • Topology management: Discovery and visualisation of the network topology across multiple vendors and domains.
  • Fault management: Correlation of alarms from multiple EMS instances to identify root cause across the network.
  • Performance management: Aggregation of performance data from multiple domains for end-to-end visibility.

Examples: Nokia NSP, Cisco WAE, Blue Planet. The NMS often serves as the integration point between the OSS orchestration layer and the EMS layer.

Domain Orchestrator

A Domain Orchestrator is a specialised orchestrator for a specific network domain (e.g., IP/MPLS, Optical Transport, Mobile Core). It manages the lifecycle of domain-specific services and resources. Unlike the EMS (which manages elements) or NMS (which manages the network), the domain orchestrator manages services within its domain:

  • Service decomposition: The domain orchestrator decomposes domain-level service orders into specific element configurations.
  • Resource management: It manages the pool of domain-specific resources (e.g., VLAN IDs, IP addresses, optical wavelengths).
  • Domain automation: It automates the creation, modification, and deletion of domain services end-to-end.

Examples: Cisco NSO (for IP/MPLS), Ciena Blue Planet MCP (for optical), Nokia NSP Domain Orchestrator. The domain orchestrator is the key southbound interface for the XDO — the XDO sends service orders to the domain orchestrator, which handles the domain-specific complexity internally.

SDN Controller

An SDN Controller is a specialised type of domain controller that separates the control plane from the data plane and provides centralised control of forwarding behaviour. SDN controllers differ from traditional EMS/NMS systems in their architecture:

  • Centralised control: The controller computes forwarding paths centrally and pushes flow entries to switches/routers via OpenFlow, P4Runtime, or similar protocols.
  • Programmatic interface: SDN controllers expose REST or gRPC APIs that allow the orchestration layer to program network behaviour directly.
  • Real-time adaptation: The controller can react to network events (congestion, failure) in real-time by re-routing traffic.

Examples: ONOS, OpenDaylight, Tungsten Fabric. In the telecom context, SDN controllers are most commonly used in data centre fabrics, optical transport, and WAN optimisation use cases.

How They Fit Together

In a typical OSS architecture, these systems form a hierarchy:

  • The Cross-Domain Orchestrator (XDO) sits at the top, receiving service orders from SOM and decomposing them into domain-specific orders.
  • Each Domain Orchestrator (e.g., Cisco NSO for IP/MPLS, Nokia NSP Domain Orchestrator for transport) receives orders from the XDO and manages the domain's internal fulfilment.
  • The domain orchestrator interacts with EMS/NMS instances to configure individual elements or with SDN controllers to program the forwarding plane.
  • EMS manages the element-level FCAPS and may provide a standardised northbound interface while handling vendor-specific southbound protocols.

This hierarchy provides separation of concerns: each layer abstracts the complexity below it, and each layer can be replaced independently as long as the interfaces between layers are preserved.

Key insight: The distinction between EMS/NMS and domain orchestrator is blurring. Modern systems like Cisco NSP combine NMS functions (topology, performance) with domain orchestration (service lifecycle management). The trend is toward unified domain controllers that offer both management and orchestration capabilities through a single API layer.

Key Takeaways

Key Takeaways

  • EMS manages individual elements (FCAPS) with vendor-specific southbound interfaces and standardised northbound APIs.
  • NMS provides network-wide topology, fault correlation, and performance aggregation across multiple EMS domains.
  • Domain Orchestrators manage the lifecycle of domain-specific services and are the key southbound interface for the XDO.
  • SDN Controllers provide centralised control of programmable forwarding planes through OpenFlow, gRPC, or P4Runtime.
  • The XDO coordinates across these systems to deliver end-to-end services, with each layer abstracting the complexity below it.
