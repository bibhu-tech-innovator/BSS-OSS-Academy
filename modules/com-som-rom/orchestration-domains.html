3.5 Orchestration Domains

How SOM Integrates with Technology Domains

What Are Orchestration Domains?

Orchestration domains are discrete technology silos within a telecom operator's network that are managed by dedicated domain controllers, element management systems (EMS), or network management systems (NMS). In the layered order management model, SOM decomposes service orders into resource-level instructions that must be dispatched to the correct orchestration domain based on the type of resource being activated, modified, or decommissioned.

Each orchestration domain has its own native protocols, data models, lifecycle management semantics, and northbound interface. SOM must therefore maintain a mapping layer that translates abstract RFS-level requests into domain-specific activation commands. This mapping is driven by the Resource Catalog (TMF634), which defines resource specifications and their associated domain affinity.

Key insight: SOM does not directly configure network elements. Instead, it delegates resource activation to domain-specific orchestration engines and ROM/NSO solutions. SOM's role is to coordinate the overall service fulfilment process across multiple domains, ensuring correct sequencing, dependency management, and state propagation.

Technology Domains and Integration Patterns

The following table summarises the primary technology domains that SOM typically interacts with, the nature of the integration, and the protocols or interfaces used to communicate with each domain.

Domain Description Integration Pattern Protocol / Interface Example Resources
Mobile Core (EPC / 5GC) Packet core network elements including MME, SGW, PGW, UPF, SMF, AMF. Handles subscriber session management, mobility, and QoS enforcement. Direct API to domain controller REST / NETCONF / Diameter APN profiles, QoS flows, subscriber data, network slices
RAN (Radio Access Network) Radio base stations, NodeB, eNodeB, gNodeB, RNC. Responsible for radio resource management and air interface configuration. Direct API to domain controller NETCONF / RESTCONF / O1 interface Cell configurations, carrier aggregation profiles, RAN slice templates
Transport (Optical / Microwave) Optical transport network elements including ROADM, OTN switches, microwave links. Provides physical and logical connectivity between sites. ROM / NSO for device configuration NETCONF / SNMP / TL1 / OpenConfig Cross-connects, VLANs, optical channels, protection paths

Service Platforms (IMS / VoLTE) IP Multimedia Subsystem (IMS), VoLTE/ VoNR cores, application servers for voice, messaging, and supplementary services. Direct API to platform REST / SIP / SOAP / TMF APIs IMPU/IMPI profiles, service triggers, media resource configurations

Direct API Integration Pattern

For domains that expose mature, standardised northbound interfaces, SOM can issue activation requests directly to the domain controller. This pattern is most common for Mobile Core, RAN, SD-WAN, and Service Platforms, where vendor-provided controllers expose RESTful or NETCONF-based APIs that can accept high-level resource specifications.

In this pattern, SOM constructs a domain-specific payload by mapping the abstract characteristics from the RFS specification (e.g., "qosProfile": "gold", "maxBitrate": "100Mbps") into the domain controller's expected format. The domain controller is responsible for translating this payload into device-level commands and managing the transactional lifecycle on the network elements it controls.

Advantages: Low latency, direct state visibility, reduced architectural complexity. SOM can read back the activation status and resource identifiers directly from the domain controller's inventory.

Disadvantages: Tight coupling to domain controller versioning and API semantics. Changes to the domain controller API may require SOM logic updates. Each domain requires a separate integration adapter within SOM.

Mobile Core Integration Example

When SOM needs to provision a new QoS flow for a 5G subscriber, it sends a request to the Mobile Core domain controller with parameters such as SUPI (subscriber identifier), DNN (data network name), 5QI (5G QoS identifier), and ARP (allocation and retention priority). The domain controller translates this into the appropriate PFCP session modifications on the UPF and SMF. SOM tracks the state of the resource order item and updates the service instance accordingly.

ROM / NSO Integration Pattern

For domains where device-level configuration is required — particularly Transport, IP Core, and legacy access networks — SOM delegates activation to ROM or a Network Services Orchestrator (NSO) such as Cisco NSO. ROM/NSO maintains the detailed device configurations, manages configuration transactions across multiple devices, and provides a consolidated northbound interface to SOM.

In this pattern, SOM issues a resource order (TMF652) to ROM, specifying the RFS to be activated. ROM decomposes this into device-level configuration changes, manages the sequencing of operations on each device, handles rollback in case of partial failure, and synchronises the resulting state to Resource Inventory (TMF639).

Advantages: Abstraction of device complexity from SOM. ROM/NSO can manage multi-vendor, multi-technology environments with transactional integrity. Configuration drift detection and remediation are handled at the ROM layer.

Disadvantages: Additional network hop and potential latency. ROM/NSO licensing costs and operational overhead. State synchronisation between SOM, ROM, and domain controllers must be carefully managed.

Transport Domain Example

Consider a business VPN order that requires a new MPLS circuit between two customer sites. The transport segment involves configuring PE routers with a new VRF, establishing an LSP across the MPLS core, and provisioning a cross-connect on the optical transport layer. SOM decomposes this into multiple RFS items and issues a resource order to ROM. ROM coordinates the NETCONF sessions to the PE routers and TL1 commands to the optical equipment, ensuring that the MPLS LSP is established before the VRF is activated, and that the optical cross-connect is provisioned before the LSP is signalled.

Catalog-Driven Domain Routing

A critical design principle in SOM is that domain routing decisions should be driven by the Resource Catalog rather than hard-coded in the orchestration logic. The Resource Specification in TMF634 includes attributes and relationships that define which domain controller handles which resource type, what protocol is used, and what mapping rules apply.

Catalog Concept Purpose Example
Resource Domain Identifies the technology domain responsible for a resource specification (e.g., "MobileCore", "IPCore", "Transport"). A resource spec for "MPLS VPN Port" has domain = "IPCore"
Domain Endpoint Specifies the API endpoint URL and authentication method for the domain controller. https://mc-controller:8443/api/v1/qos
Protocol Binding Maps abstract RFS characteristics to domain-specific payload parameters. CFS "bandwidth" → RFS "committedInfoRate" → domain API "cir"
Orchestration Strategy Defines whether the domain is integrated directly or via ROM/NSO, and what failure semantics apply. "direct", "rom", "nso", "batch", "sequential"
Domain Capability Describes what operations a domain supports (create, read, update, delete, test, suspend, restore). IPCore supports CRUD for VRFs and QoS policies
Characteristic Mapping Transformation rules between service-level characteristics and resource-level parameters. RFS.speed → domain.bandwidthProfile with unit conversion

When ROM receives a resource order item from SOM, it looks up the resource specification in the catalog, determines the target domain from the Resource Domain attribute, reads the Domain Endpoint and Protocol Binding, and constructs the appropriate API request. This catalog-driven approach means that adding a new domain or modifying an existing integration does not require changes to the core orchestration engine — only updates to the catalog entries.

Per-Domain Engine Mapping

Operators who manage a heterogeneous network with multiple technology generations often deploy a dedicated orchestration engine per domain. For example, a single operator might run:

  • Mobile Core Orchestrator: A specialised controller for 4G EPC and 5GC that handles subscriber profiles, session management, and network slicing. Typically provided by the core network vendor (e.g., Ericsson, Nokia, Huawei) and integrated via vendor-specific APIs.
  • RAN Orchestrator: A radio-specific controller that manages cell configurations, carrier aggregation, RAN slicing, and radio resource management. Often integrated via the O-RAN O1 interface or vendor-proprietary REST APIs.
  • Transport / IP NSO: A multi-vendor network services orchestrator (e.g., Cisco NSO, Huawei iMaster NCE) that manages the IP/MPLS and optical domains via NETCONF and vendor YANG models.
  • Service Platform Orchestrator: A controller for IMS/VoLTE services that manages subscriber provisioning, service triggers, and media resource allocation.
  • Cloud / NFV Orchestrator: An NFV MANO stack (e.g., Open Source MANO, VMware Telco Cloud) that manages VNF lifecycle, virtual network resources, and cloud infrastructure.

SOM must maintain a registry of these domain engines and their capabilities. When a service order is decomposed, SOM determines which domains are involved and dispatches the appropriate instructions to each domain engine. SOM tracks the overall service order state as an aggregate of the individual domain states, applying compensating actions if any domain reports a failure.

Cross-Domain Coordination Challenges

Coordinating fulfilment across multiple orchestration domains introduces several architectural challenges:

  • Sequencing: Some domains have strict ordering constraints. For example, the IP Core VRF must be created before the transport LSP can be signalled, and both must be completed before the customer-facing service can be declared active. SOM must enforce these sequencing constraints without introducing unnecessary serialisation that would impact overall order throughput.
  • Idempotency: Domain controllers may receive duplicate requests due to network issues or SOM retry logic. Each domain controller must implement idempotent operations to prevent duplicate resource creation. SOM should include idempotency keys in API requests and handle 409 Conflict responses gracefully.
  • Partial Failure: When a service order spans multiple domains, it is possible for some domains to succeed while others fail. SOM must implement compensation logic — rolling back successfully completed domain operations when a downstream domain fails. This requires each domain controller to support a "rollback" or "delete" operation for previously created resources.
  • State Synchronisation: Domain controllers maintain their own view of resource state. SOM must periodically reconcile its view of service instance state against the domain controllers' actual state, especially after network outages or manual interventions. This reconciliation is typically performed by a periodic audit job that compares inventory records.
  • Latency and Timeouts: Different domains have vastly different activation times. A cloud VNF instantiation might take 20 minutes, while a simple ACL update takes seconds. SOM must support asynchronous processing with configurable timeouts, long-running task tracking, and webhook-based status notification.

Design guidance: Each domain controller should expose a standardised northbound interface that supports the lifecycle operations relevant to that domain (create, read, update, delete, test, suspend, restore). SOM should treat each domain as a black box with well-defined state transitions, avoiding assumptions about internal domain behaviour.

Future-Proofing Domain Integration

As operators adopt cloud-native architectures, open RAN, and network slicing, the role of orchestration domains continues to evolve. Key trends include:

  • Intent-based interfaces: Instead of specifying exact resource parameters, SOM expresses a high-level intent (e.g., "provide 100 Mbps connectivity between sites A and B with latency below 10 ms"), and the domain controller determines the optimal resource configuration. Intent-based interfaces reduce coupling and allow domain controllers to optimise within their technology domain.
  • Closed-loop assurance integration: Domain controllers increasingly expose performance metrics and fault information alongside resource state. SOM can use this data to trigger service healing workflows — for example, re-routing a service over an alternative transport path when the primary path degrades.
  • Standardised YANG models: The adoption of OpenConfig and IETF YANG models as a common representation for network configuration is reducing the integration effort for each domain. SOM and ROM can use YANG-based tooling to validate configuration payloads before dispatching them to domain controllers.
  • Orchestration mesh: Rather than SOM being the single centralised coordinator, some operators are adopting a distributed orchestration mesh where domain controllers communicate directly with each other for cross-domain resource coordination, with SOM acting as the initial trigger and final aggregator.

Key Takeaways

  • Orchestration domains are discrete technology silos (Mobile Core, RAN, Transport, IP Core, Service Platforms) each managed by a dedicated domain controller with its own protocols and semantics.
  • Two primary integration patterns exist: direct API to domain controllers (for Mobile Core, RAN, SD-WAN, Service Platforms) and ROM/NSO delegation for device-level configuration (Transport, IP Core, Access).
  • Catalog-driven routing ensures that SOM dispatches resource orders to the correct domain controller based on Resource Specification attributes rather than hard-coded logic.
  • Per-domain engines allow operators to use best-in-breed controllers for each technology domain while SOM coordinates the overall service fulfilment process.
  • Cross-domain coordination requires handling sequencing constraints, idempotency, partial failure with compensation, state synchronisation, and heterogeneous activation latencies.
  • Future trends include intent-based interfaces, closed-loop assurance integration, standardised YANG models, and distributed orchestration meshes.
