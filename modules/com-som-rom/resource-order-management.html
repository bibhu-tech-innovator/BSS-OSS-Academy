3.4 Resource Order Management (ROM)

Resource Allocation, Activation, and Inventory Management

Resource Order Management (ROM) is the bottom layer of the three-layer order model. It is responsible for allocating, configuring, activating, and decommissioning the physical and logical network resources that deliver telecom services. ROM sits at the boundary between the OSS service layer and the network infrastructure — translating abstract resource requirements from SOM into concrete activation commands that domain controllers and network element managers execute.

Unlike COM and SOM, which operate primarily on logical entities (product offerings, service specifications), ROM deals directly with the network: routers, switches, firewalls, optical transport equipment, base stations, virtual network functions (VNFs), and the configuration commands that control them. ROM must handle the complexity of multi-vendor, multi-technology, and multi-domain network environments while abstracting this complexity from the layers above.

Key insight: ROM is the layer where the "rubber hits the road" in telecom fulfilment. A commercial order can be perfectly captured (COM), a service can be beautifully designed (SOM), but neither matters if the resource layer cannot reliably activate the configuration on the network. The quality of a telco's ROM implementation directly determines order success rates, activation times, and operational efficiency.

Resource Order Decomposition

When SOM submits a resource order to ROM, it contains a set of resource requirements that describe what network resources are needed to deliver each RFS instance. ROM's first task is to decompose these requirements into actionable resource order items.

The Decomposition Flow

RFS Requirement → Resource Spec Lookup → Resource Candidate Resolution → Create Resource Order Items → Dispatch to Domain Controller
  1. Receive resource requirements: ROM receives a TMF652 Resource Order from SOM. Each service order item in SOM may generate multiple resource requirements that are packed into a single resource order.
  2. Resource specification lookup: For each resource requirement, ROM retrieves the corresponding Resource Specification from the Resource Catalog (TMF634). The specification defines the resource type, allowed characteristics, configuration templates, and activation protocols.
  3. Resource candidate resolution: ROM searches the Resource Inventory (TMF639) for available resource candidates that match the specification requirements. For example, a requirement for "10G Ethernet Port at Site A" might resolve to specific port "PE01-Gig0/0/1" on a provider edge router. This step may involve:
    • Checking physical inventory for available ports and capacity.
    • Reserving IP addresses, VLAN IDs, MPLS labels, or other logical resource pools.
    • Validating that the candidate resource supports the required characteristics (e.g., QoS profiles, encapsulation types).
  4. Create resource order items: ROM creates order items for each resource to be allocated or configured. Each item specifies the resource action (add, modify, delete), the target resource instance (or a placeholder for new resources), and the configuration characteristics.
  5. Dispatch to domain controller: ROM dispatches the configuration commands to the appropriate domain controller or network element manager using the protocol specified in the resource specification (NETCONF, RESTCONF, SNMP, CLI, vendor API, etc.).

The Activation Sequence

Activation — the process of pushing configuration changes to network devices — must follow a strict ordering to avoid service disruption and configuration errors. ROM is responsible for orchestrating this sequence based on dependencies between resource order items and the requirements of each domain.

Typical Activation Ordering for an MPLS VPN Service

  1. Physical layer: Ensure physical connectivity is established. Provision access circuit, verify optical signal, enable ports.
  2. Transport layer: Configure transport-level parameters. Set MTU, enable VLAN tagging, configure encapsulation.
  3. IP layer: Assign IP addressing. Configure interface IP addresses, loopback addresses, and routing adjacencies.
  4. MPLS / VPN layer: Configure MPLS labels, LDP or RSVP-TE signalling, and VRF instances with route targets.
  5. QoS layer: Apply service-level traffic policies. Configure shaping, policing, marking, and queuing.
  6. Service activation: Enable the service. Activate BGP sessions, verify routing table population, and perform end-to-end connectivity tests.
  7. CPE (if managed): Configure customer premises equipment. Deploy zero-touch configuration, verify WAN connectivity, and test customer LAN ports.

This ordering is enforced by the activation sequence engine within ROM, which maintains a directed acyclic graph (DAG) of resource order item dependencies. An item cannot begin activation until all of its prerequisite items have completed successfully.

Activation Protocols and Interfaces

ROM communicates with domain controllers and network elements through a variety of protocols, depending on the network technology and vendor:

  • NETCONF / YANG: IETF standard for configuration management. Used with modern routers, switches, and optical equipment. NETCONF provides transactional, rollback-capable configuration operations.
  • RESTCONF: RESTful adaptation of NETCONF, using HTTP and JSON/XML. Commonly used with cloud-native network functions.
  • SNMP: Legacy protocol for configuration and monitoring. Still widely used for read operations and basic set operations on older equipment.
  • CLI / SSH: Direct command-line interface. Used where structured protocols are not available, often abstracted by device driver adapters.
  • gRPC / gNMI: Google RPC-based interface for streaming telemetry and configuration. Increasingly adopted in SDN and cloud-native networking.
  • Vendor-specific APIs: Cisco NSO, Juniper Contrail, Nokia Nuage, Huawei NCE, and other vendor orchestrators provide their own northbound interfaces.

Rollback and Compensation Patterns

One of ROM's most critical responsibilities is handling failures during activation. When a resource order item fails, ROM must execute a rollback to undo any partially completed work and restore the network to a consistent state. Unlike COM and SOM (which operate on logical records), ROM rollbacks involve changing real network configuration, which carries operational risk.

Rollback Strategies

Strategy Description When to Use Risk Level
Transactional (NETCONF) All configuration changes for an order item are bundled into a single NETCONF transaction. If any change fails, the entire transaction is rolled back atomically. Available when domain controllers support NETCONF/YANG with confirmed-commit. Low — transaction boundaries are managed by the protocol.
Reverse-order compensation ROM maintains a journal of every configuration change applied. If a failure occurs, the journal is traversed in reverse order, applying the inverse of each change. When transactional support is unavailable or when rollback spans multiple devices/domains. Medium — inverse operations must be correctly defined and may themselves fail.
Configuration snapshot / restore Before making changes, ROM captures the current device configuration (or a relevant subset). On failure, the saved configuration is restored. When changes affect a well-defined portion of device configuration and the device supports configuration replace. Medium — restore may conflict with concurrent changes from other orders.
Manual compensation ROM marks the failed order item and alerts operations staff to manually resolve the issue and clean up partial configuration. When automated rollback is too risky (e.g., partial multi-device changes with complex dependencies). High — human error, slow resolution, operational overhead.
Orchestrated multi-domain rollback For resource orders spanning multiple domain controllers, ROM coordinates a phased rollback across all affected domains, ensuring consistency at each step. For complex orders involving access, aggregation, core, and CPE domains. Medium — requires careful coordination and timeout management.

Compensation Journal Example

The following table illustrates a compensation journal for a failed resource order item. Each forward action has a corresponding inverse action that would be executed during rollback:

Sequence Forward Action Target Status Compensation Action
1 Set interface MTU 9216 PE01-Gig0/0/1 Completed Restore MTU to default (1500)
2 Create VRF CUST-A PE01 Completed Delete VRF CUST-A
3 Assign IP 10.0.0.1/30 to interface PE01-Gig0/0/1 Completed Remove IP address from interface
4 Configure BGP neighbor 10.0.0.2 PE01 Completed Remove BGP neighbor configuration
5 Apply QoS policy "GOLD" to interface PE01-Gig0/0/1 Failed Rollback steps 4, 3, 2, 1 (reverse order)

Design pattern: The Compensation Journal (also called the "Undo Log" or "Change Log") is a critical component of any production ROM system. Every configuration change MUST be recorded with enough detail to compute its inverse. The journal is typically stored in a database that is separate from the network device configurations, providing a durable record of all activation activity for audit, compliance, and troubleshooting purposes.

Resource State Management

ROM maintains the state of each resource order and resource order item through a lifecycle that parallels COM and SOM but includes additional states specific to network activation.

State Description Network Status
Submitted The resource order has been received from SOM and accepted for processing. No changes made to network.
Assessing Resources ROM is checking resource availability and reserving candidates from inventory. Resource pool reservations made, no device configuration.
Allocated Resources have been selected and reserved. Resource instances created in inventory. Resource instances recorded but not yet configured on devices.
Configuring Configuration commands are being pushed to domain controllers or network elements. Device configuration in progress. Some devices may be partially configured.
Active All configuration changes have been successfully applied and verified. Network configured and operational.
Pending Activation Resources are allocated and configured but not yet service-affecting (e.g., ports admin-down awaiting scheduled cutover). Configured but not enabled. Customer not yet impacted.
Failed One or more configuration actions failed. Rollback has been executed. Partially configured state has been cleaned up and rolled back.
Cancelled The resource order was cancelled before completion. Any allocated resources have been released. All changes rolled back. Inventory updated.

Resource Inventory Synchronization

A critical function of ROM is keeping the Resource Inventory (TMF639) synchronised with the actual state of the network. This is known as inventory reconciliation and is essential for ensuring that future resource assignments are based on accurate data.

Synchronization Mechanisms

  • Transactional updates: When ROM successfully completes a configuration change, it immediately updates the Resource Inventory to reflect the new state. For example, setting a port MTU from 1500 to 9216 updates the port resource instance in inventory.
  • Configuration drift detection: Periodic or event-driven reconciliation jobs compare the Resource Inventory against the actual device configuration. Discrepancies (drift) are flagged for investigation.
  • Network discovery: ROM or associated discovery tools periodically scan the network to detect new devices, interfaces, and connections, updating the inventory accordingly.
  • Resource pool management: Logical resource pools (IP addresses, VLAN IDs, MPLS labels) are managed through a reservation and release mechanism. ROM reserves resources before activation and releases them back to the pool on deactivation or rollback.

ROM Integration Patterns

ROM sits at the bottom of the order management stack and integrates with both northbound (SOM) and southbound (network) systems:

  • SOM (Upstream): Receives TMF652 resource orders from SOM. Sends state change notifications back to SOM.
  • Resource Catalog (Reference): Reads resource specifications (TMF634) to determine resource characteristics, configuration templates, and activation protocols.
  • Resource Inventory (Sink): Writes resource instance data to the Resource Inventory (TMF639). Reads inventory for resource candidate selection.
  • Domain Controllers (Southbound): Translates resource order items into domain-specific configuration commands. Examples: SDN controllers (ONAP, Cisco NSO), NFV orchestrators (OpenStack MANO), EMS/NMS systems.
  • Network Elements (Southbound, via Domain Controller): The actual routers, switches, firewalls, base stations, and optical equipment that receive configuration commands.
  • Activation Monitoring (Internal): ROM monitors the progress and success of configuration changes, collecting response times, error messages, and device logs.
  • Assurance Systems (Reference): Resource state changes from ROM are published to service assurance systems for monitoring and alerting.

Performance and Scalability Considerations

ROM is typically the most performance-sensitive layer in the order management stack. Activation delays directly impact customer experience and order-to-cash cycle times. Key architectural considerations include:

  • Concurrent activation capacity: ROM must be able to handle hundreds or thousands of simultaneous activation requests across multiple domains without contention.
  • Idempotency: Configuration commands should be idempotent — applying the same command multiple times should produce the same result. This is essential for retry handling.
  • Timeout management: Network activation operations can be slow (seconds to minutes). ROM must implement robust timeout, retry, and escalation mechanisms.
  • Device locking: To prevent concurrent conflicting changes to the same device, ROM typically implements device-level locking or uses transactional configuration protocols.
  • Asynchronous execution: ROM operations are inherently asynchronous. The ROM engine dispatches activation commands and then polls or waits for completion notifications rather than blocking on a synchronous response.

Key Takeaways

  • ROM is the bottom layer of the three-layer order model, responsible for allocating, configuring, and activating network resources based on requirements from SOM.
  • Resource order decomposition translates RFS requirements into concrete resource order items, resolving abstract requirements against the Resource Catalog and Resource Inventory.
  • Activation sequencing is critical — resources must be configured in the correct order (physical → transport → IP → MPLS → QoS → service) to ensure successful service delivery.
  • Rollback and compensation in ROM is more complex than in COM or SOM because it involves reverting real network configuration changes. Transactional protocols (NETCONF) and compensation journals are essential patterns.
  • Resource inventory synchronisation ensures that the inventory database accurately reflects the actual network state, enabling reliable resource assignment for future orders.
  • TMF652 Resource Ordering API provides the standardised interface for ROM, defining resource order states, actions, and notification patterns.
  • Scalability and performance are critical ROM concerns — the system must handle high concurrency, implement idempotent operations, manage timeouts, and prevent conflicting device changes through locking.
  • Protocol diversity is a key challenge: ROM must support NETCONF, RESTCONF, SNMP, CLI, gNMI, and vendor-specific APIs across different domains and device types.
