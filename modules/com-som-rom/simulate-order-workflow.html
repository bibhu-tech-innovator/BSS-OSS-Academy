3.9 Simulate Order Workflow

End-to-End Order Flow Simulation

Why Simulate an Order Workflow?

In a production BSS/OSS environment, an order passes through dozens of systems, state transitions, validation gates, and orchestration steps before a customer’s service goes live. Understanding this end-to-end flow is essential for architects, developers, and operations teams who need to troubleshoot failures, optimise throughput, and design resilient order lifecycles.

Simulating the order workflow reveals the hidden coupling between systems, the timing constraints imposed by manual approval gates, and the data transformation rules that govern how a commercial product offering becomes a configured network resource. It also exposes failure modes that are difficult to reproduce in a test environment—race conditions between concurrent order items, partial rollback scenarios, and the ripple effect of a resource activation timeout on the commercial order state.

Key insight: An end-to-end order simulation is not just a training exercise. It is a critical design artefact that validates the decomposition rules, state propagation logic, and error-handling strategies before any code is deployed to production. Operators who run regular order simulations detect integration defects 60% faster than those who rely on unit tests alone.

The End-to-End Order Journey

The following table traces a single commercial order for a business MPLS VPN with three sites through every system involved in the BSS/OSS stack. Each row represents a discrete step in the workflow, the system that owns that step, the action performed, and the data record produced at that stage.

Step System Action Data Produced
1. Lead Capture CRM (Salesforce / Siebel) Sales rep creates an opportunity for a 3-site MPLS VPN with 100 Mbps committed information rate per site. Customer credit score is checked pass. Opportunity record with customer ID, service address, desired start date, and preliminary contract term.
2. CPQ Configuration CPQ (Salesforce CPQ / Apttus) Sales rep selects product bundle "Business MPLS VPN 3-Site" from the product catalog. Characteristics are captured: CIR=100Mbps, VLAN ID pool, QoS class=Gold. Contract term is set to 36 months. Configured quote with product offering ID, line items, pricing, characteristics, and contract terms.
3. Pricing & Approval CPQ / CRM List price is retrieved from the product catalog. Volume discount rule (15% for 3+ sites) is applied. The quote total exceeds the sales rep authority threshold, triggering a manager approval workflow via email. Priced quote with discount breakdown, tax calculation, and approval request record with status "Pending Approval".
4. Order Submission CRM / Order Capture Manager approves the quote. Sales rep submits the order. The order capture system validates mandatory fields, checks product availability, and creates a commercial order via TMF622. TMF622 Product Order (state: Submitted) with order items mapping to the product offering IDs.
5. Order Validation COM (Order Hub) COM receives the TMF622 product order. It validates customer eligibility against CRM (TMF629), checks for duplicate orders, runs commercial eligibility rules, and transitions the order to "In Progress". Validated order object with enriched characteristics, customer eligibility status, and fraud check results.
6. Product Decomposition COM / Product Catalog COM queries the Product Catalog (TMF620) to retrieve the product specification structure. The "Business MPLS VPN 3-Site" offering decomposes into three CFS specifications: "MPLS VPN Port" per site, "MPLS VPN Transport", and "QoS Gold Profile". Decomposition map: product offering ID to CFS specification IDs with characteristic mappings and cardinality rules.
7. Service Order Creation COM / SOM COM calls TMF641 Service Ordering API on the SOM system, passing the CFS specifications, characteristics, and customer context. A service order is created with one order item per CFS. TMF641 Service Order (state: Submitted) with line items referencing CFS specifications and their characteristics.
8. Service Design SOM / Service Catalog SOM retrieves the service specification from the Service Catalog (TMF633). Each CFS has an associated service topology that defines its relationship to RFS resources. The "MPLS VPN Port" CFS decomposes into "Physical Port" RFS and "Logical Interface" RFS. Service topology design with CFS-to-RFS mappings, relationship types (uses / depends-on), and characteristic inheritance rules.
9. Resource Order Creation SOM / ROM SOM calls TMF652 Resource Ordering API on the ROM system. A resource order is created with order items for each RFS: physical port allocation, VLAN provisioning, QoS policy creation, and IP address assignment. TMF652 Resource Order (state: Submitted) with resource order items referencing RFS specifications and target network domains.
10. Resource Allocation ROM / Resource Catalog ROM queries the Resource Catalog (TMF634) to determine resource candidates. It identifies available physical ports on the edge router, VLAN ID pool ranges, and QoS policy templates for the Gold class. Resource allocation plan mapping each RFS order item to a specific resource candidate (device ID, port ID, VLAN range).
11. Network Activation ROM / Domain Controllers ROM dispatches activation commands to domain controllers: NETCONF to the IP/MPLS domain for MPLS configuration, RESTCONF to the SD-WAN controller for policy enforcement, and SNMP to the access aggregation switch for VLAN provisioning. Activation request records per domain with device configuration payload, transaction ID, and expected completion timeout.
12. Activation Confirmation Domain Controllers / ROM Each domain controller confirms successful configuration. ROM receives confirmation callbacks, updates resource order item states to "Completed", and records the resource instances in the Resource Inventory (TMF639). TMF639 Resource Inventory records with device identifiers, interface names, VLAN IDs, QoS policy references, and IP addresses.
13. Service Activation SOM / SLM ROM notifies SOM that all resource orders for a given CFS are completed. SOM transitions the corresponding service order items to "Completed" and creates service instance records in the Service Inventory / SLM (TMF638). TMF638 Service Inventory records: CFS instances with service ID, characteristics, and references to underlying resource instances.
14. Commercial Order Completion COM SOM notifies COM that all service order items are completed. COM transitions the commercial order to "Completed". The product order status is updated to reflect that delivery is fulfilled. Completed TMF622 Product Order with final state, service IDs, activation timestamps, and audit trail.
15. Billing Activation Billing System / COM COM publishes a billing activation event to the billing system. The billing system creates a recurring charge schedule for the MPLS VPN service at the agreed price. One-time installation fees are invoiced immediately. Billing account entry with recurring charge plan, installation fee invoice, and service-to-billing-item mapping.
16. Service Assurance Handoff Assurance System The assurance system ingests the service instance and resource instance data to configure monitoring. Thresholds are set for CIR utilisation (95% alert), latency (50ms warning, 100ms critical), and availability (99.9% SLA). Monitoring configuration records with alarm thresholds, performance management KPIs, and SLA breach notification rules.
17. Customer Notification CRM / Notification Engine CRM sends a service activation confirmation email to the customer. The notification includes service IDs, activation date, next billing date, and a link to the customer portal for service management. Outbound notification record with delivery status, template used, and customer communication preference (email/SMS).
18. Order Archival COM / Data Lake The completed order record, along with all service and resource order data, is archived to the data lake for analytics, regulatory compliance, and historical reporting. The data lake applies retention policies based on data classification. Parquet files in the data lake with order data partitioned by date, order type, and customer segment for downstream BI reporting.

State Propagation Across Layers

One of the most critical aspects of the order simulation is understanding how state changes propagate between the COM, SOM, and ROM layers. These propagation rules determine what happens when an individual order item fails, how partial fulfilment is represented, and whether downstream compensation is triggered automatically.

The following propagation rules are observed in the simulation:

  • Forward propagation (top-down): When a commercial order item transitions to "In Progress", SOM receives a notification and begins processing the corresponding service order items. Similarly, when a service order item enters "In Progress", ROM begins processing the resource order items. The top-down flow ensures that work begins at each layer as soon as the parent layer is ready.
  • Backward propagation (bottom-up): When a resource order item completes or fails, ROM notifies SOM, which updates the corresponding service order item state. SOM then notifies COM, which updates the commercial order item state. Failure at any layer must be propagated upward within configurable timeout windows.
  • Partial fulfilment: A service order item that references five resource order items may complete even if only four resource items succeed, provided the service specification defines a minimum completion threshold (e.g., 80% of resources must be active). The fifth failed resource item enters a compensation state.
  • Compensation chains: When a resource activation fails after other resources have already been provisioned, ROM executes a compensation plan: deactivate the provisioned resources, release the IP addresses, and return the VLAN IDs to the pool. The compensated state is propagated upward as an "Item Failed" with a compensation detail.

Simulation Failure Scenarios

No order simulation is complete without exercising the failure paths. The following scenarios are commonly simulated to validate the resilience of the order management architecture:

Scenario 1: Resource Exhaustion

During step 10 (Resource Allocation), the ROM system discovers that the edge router at one site has no available physical ports. The resource order item for that site enters "Failed" with reason code "PORT_EXHAUSTION". SOM receives the failure notification and checks whether the service specification allows an alternative resource candidate. If the specification defines a secondary router as a fallback, SOM instructs ROM to retry on the alternate device. Otherwise, the service order item transitions to "Failed", and the commercial order item enters a "Partially Fulfilled" state awaiting manual intervention.

Scenario 2: Domain Controller Timeout

During step 11 (Network Activation), the NETCONF domain controller for the IP/MPLS domain does not respond within the configured timeout window (120 seconds). ROM retries twice with exponential backoff. After three total attempts, the activation record is marked "Failed_Timeout". ROM transitions the resource order item to "Failed" and initiates compensation for any resources that were successfully provisioned in other domains. The service order item enters a "Pending Manual Recovery" state, and an operations ticket is automatically raised in the OSS ticketing system.

Scenario 3: Order Cancellation Mid-Flight

A customer calls to cancel the order after the service order has been created but before resource activation has completed. COM transitions the commercial order to "Cancellation Pending" and sends a cancellation request to SOM. SOM evaluates which service order items are in a cancellable state (items in "Submitted" or "Pending" are cancelled immediately; items in "In Progress" with active resource orders require a compensatable check). ROM receives cancellation instructions for resource order items that have not yet been activated; items that are already activated are scheduled for deactivation within a maintenance window. The commercial order transitions to "Cancelled" only after all child items are confirmed cancelled or decommissioned.

Simulation Tooling and Techniques

Operators typically implement order workflow simulation using a combination of the following approaches:

  • BPMN 2.0 Simulation Engines: Tools such as Camunda, Flowable, or IBM BPM allow architects to model the order workflow as a BPMN diagram and simulate the execution of tokens through the process. Each lane in the diagram corresponds to a system boundary (CRM, COM, SOM, ROM, Domain Controller). Simulation reports show cycle time, bottleneck activities, and resource utilisation per lane.
  • API Mock Servers: WireMock, MockServer, or Postman Mock Servers simulate the TMF API endpoints (TMF620, TMF622, TMF629, TMF633, TMF638, TMF641, TMF634, TMF639, TMF652) with configurable response delays, error rates, and state machines. This allows the order management test harness to simulate realistic network latency and failure conditions.
  • Chaos Engineering: Tools like Chaos Monkey or LitmusCHAOS are integrated into the simulation pipeline to inject random failures: API timeouts, database connection drops, message queue backpressure, and network partition events. The simulation measures how many concurrent failures the order management system can tolerate before violating the SLA for order completion time.
  • Data Lineage Tracing: OpenTelemetry tracing with Jaeger or Zipkin provides end-to-end visibility into each order's journey. Each simulation run produces a trace tree that shows the timing and success/failure of every API call, state transition, and database operation. Traces that exceed the expected duration are flagged for analysis.

Simulation Metrics and KPIs

A comprehensive order simulation measures the following key performance indicators to validate that the order management architecture meets its design objectives:

  • Order Cycle Time: The elapsed time from order submission to commercial order completion. Target: under 5 minutes for fully automated orders, under 4 hours for orders requiring manual approvals.
  • Decomposition Latency: The time taken for COM to decompose a product offering into CFS specifications and create the service order. Target: under 500 milliseconds per order item.
  • Resource Activation Time: The time taken for ROM to activate all resources for a given CFS, measured from resource order creation to activation confirmation. Target: under 60 seconds for software-configured resources, under 15 minutes for resources requiring physical intervention.
  • State Propagation Delay: The time between a state change at the ROM layer and the corresponding state update at the COM layer. Target: under 5 seconds end-to-end.
  • Failure Recovery Rate: The percentage of simulated failures that are automatically recovered through compensation and retry mechanisms without manual intervention. Target: 95% of resource-level failures, 80% of service-level failures.
  • Throughput: The maximum number of concurrent order simulations the system can process without exceeding the cycle time target. Target: 50 concurrent orders for a Tier-2 operator, 200+ for a Tier-1 operator.

Key Takeaways

  • The end-to-end order journey spans 18 distinct steps across CRM, CPQ, COM, SOM, ROM, Domain Controllers, SLM, Billing, Assurance, and Data Lake systems. Each step produces structured data that must be traceable back to the original commercial order.
  • State propagation is bidirectional: top-down propagation triggers downstream work, while bottom-up propagation reports results. Failure at any layer must be propagated upward within configurable timeout windows to maintain data consistency.
  • Partial fulfilment and compensation chains are first-class concerns. Service specifications define minimum completion thresholds, and ROM maintains compensation plans for every resource order to enable clean rollback of partially completed activations.
  • Failure scenarios (resource exhaustion, domain controller timeouts, mid-flight cancellation) must be simulated to validate the order architecture’s resilience and to determine whether automatic recovery or manual intervention is required.
  • Simulation tooling includes BPMN simulation engines, API mock servers with configurable failure injection, chaos engineering platforms, and OpenTelemetry-based distributed tracing for end-to-end visibility.
  • Quantitative KPIs (cycle time, decomposition latency, activation time, propagation delay, failure recovery rate, throughput) must be measured in every simulation to validate architectural decisions and identify optimisation opportunities.
