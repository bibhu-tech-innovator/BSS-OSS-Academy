3.3 Service Order Management (SOM)

Service Design, CFS/RFS Decomposition, and Lifecycle Orchestration

Service Order Management (SOM) is the middle layer of the three-layer order model. It bridges the gap between what the customer buys (captured in the commercial order) and what the network delivers (handled by resource orders). SOM operates on service specifications — Customer Facing Services (CFS) and Resource Facing Services (RFS) — as defined in the Service Catalog (TMF633). A service order is a request to create, modify, delete, or otherwise manage a set of service instances that together deliver the product the customer ordered.

SOM is often described as the "brain" of the order orchestration chain. It is responsible for service design, where the logical topology of the service is defined; for service decomposition, where each CFS is broken down into its constituent RFS and resource requirements; and for lifecycle management, where the state of each service instance is tracked from inception through activation to eventual decommissioning.

Key insight: The separation between CFS and RFS within SOM is critical. CFS represents the service as the customer experiences it — e.g., "Business MPLS VPN with 100Mbps CIR at 5 sites." RFS represents the service as the network implements it — e.g., "MPLS L3VPN VRF configuration with QoS policy H on all PE routers." This separation allows service designers to create technology-agnostic CFS definitions that can be mapped to multiple RFS implementations as network technology evolves.

Service Order Business Objects

The TM Forum TMF641 Service Ordering API defines a set of business objects that form the core data model for SOM. Understanding these objects is essential for designing service order interfaces and orchestrating the service lifecycle.

Business Object TMF641 Representation Description Key Attributes
Service Order ServiceOrder The top-level order entity. Contains header information (order date, external ID, priority, requested completion date) and a list of service order items. id, externalId, priority, state, orderDate, requestedCompletionDate, relatedParty
Service Order Item ServiceOrderItem A line item within the service order, specifying a single service action (add, modify, delete, etc.) for a specific service specification or existing service instance. id, action, state, service, serviceSpecification, serviceRelationship
Service Specification ServiceSpecificationRef A reference to a service specification defined in the Service Catalog (TMF633). Determines the structure, characteristics, and allowed actions for the service. id, name, version, href, type (CFS or RFS)
Service Instance Service The actual service instance being created, modified, or deleted. Contains the current state and characteristics of the service. id, serviceState, serviceType, serviceCharacteristic, relatedService
Service Characteristic ServiceCharacteristic A key-value pair capturing a specific attribute of the service (e.g., bandwidth = "100Mbps", vlanId = "1200"). name, value (or valueType for complex values)
Service Relationship ServiceRelationship Defines how this service relates to other services. Relationship types include "reliesOn", "bundledIn", "covers", "connectsTo", and "dependsOn". relationshipType, service (reference to related service)
Order Item Relationship OrderItemRelationship Defines dependencies between order items within the same service order (e.g., item B must be completed before item C can start). relationshipType, orderItem (reference to related item)
Resource Requirement ResourceRequirement (embedded) Specifies the resource requirements for the service order item. These will be fulfilled by the ROM layer through resource orders. resourceSpecification, quantity, resourceCharacteristic, placeholderRef

SOM State Model

The TMF641 standard defines a state machine for service orders and their items. The state model governs the lifecycle of each service order item and determines what actions are allowed at each stage. Understanding the state model is essential for designing robust orchestration workflows.

Service Order States

State Description Transitions To Orchestration Significance
Submitted The service order has been received from the COM layer and accepted for processing. In Progress, Rejected SOM validates the order structure and the referenced service specifications.
Rejected The service order failed validation. The request is returned to COM with error details. Submitted (after correction) Typically caused by invalid service specification references or missing mandatory characteristics.
In Progress The service order is being processed. Service instances are being created or modified, and resource orders may have been dispatched. Pending, Completed, Failed, Cancelled Primary processing state. SOM executes service design and decomposition logic.
Pending The order is awaiting an external event or manual intervention (e.g., site survey, third-party circuit delivery). In Progress, Cancelled Order is blocked. SOM may start timer-driven escalation workflows.
Completed All service order items have been successfully fulfilled. Services are active in the SLM installed base. Terminal state SOM notifies COM of completion. Post-activation billing triggers may fire.
Failed One or more items could not be fulfilled. Compensation has been executed at the service and resource levels. Terminal state SOM executes rollback on any partially completed items and notifies COM.
Cancelled The order was terminated before completion. All in-progress work has been halted and compensated. Terminal state Cancellation may be initiated by COM or directly by a service operations agent.

Service Instance States (SLM Installed Base)

In addition to the service order state, each service instance tracked in the SLM (Service Level Management) installed base has its own lifecycle state:

State Description Transition Trigger
Feasibility The service has been designed but not yet committed. Capacity checks and pre-qualification are running. Service design initiated
Designed The service topology is designed and documented. Resource requirements are defined but not yet allocated. Design completed
Reserved Resources have been reserved for this service but not yet activated. The service exists as a reservation in inventory. Resource reservation confirmed
Active The service is fully operational. Resources are allocated and configured. The customer can use the service. Activation completed
Suspended The service is temporarily disabled while preserving configuration and resource assignments. Suspension request from COM or operations
Terminated The service has been decommissioned. Resources are released and the service record is archived. Disconnection completed

Service Order Item Actions

Each service order item includes an action attribute that determines what operation is to be performed on the referenced service specification or existing service instance. The TMF641 standard defines the following action types:

Action Description Service Instance State Transition Impact on Resource Layer Compensation Behaviour
add Create a new service instance based on the referenced service specification. None → Feasibility → Designed → Reserved → Active Creates resource orders to allocate and activate resources. If downstream fails, delete the service instance and release any reserved resources.
modify Change characteristics of an existing service instance. Active → (modify in progress) → Active Creates resource orders to reconfigure affected resources. Revert characteristic changes and roll back resource reconfigurations.
delete Decommission an existing service instance and release its resources. Active → Terminated Creates resource orders to deactivate and release resources. If deletion fails, re-activate the service and restore resources (rarely needed).
suspend Temporarily disable a service while preserving its configuration and resource assignments. Active → Suspended Creates resource orders to apply access controls or administrative down. Restore action reverts the suspension.
restore Re-enable a previously suspended service, returning it to active operation. Suspended → Active Creates resource orders to remove suspension configurations. If restore fails, re-apply suspension (fallback).

CFS Decomposition: The Core of SOM Logic

The most important function of the SOM layer is CFS decomposition — breaking down a Customer Facing Service into its constituent Resource Facing Services and their resource requirements. This is the middle step in the three-layer decomposition chain.

CFS: Managed MPLS VPN — "Business VPN 100Mbps at Site A"
↓ SOM Decomposition
RFS: MPLS Port (PE-facing)
RFS: MPLS VPN (L3VPN VRF)
RFS: QoS Policy Set
RFS: CPE Management (if managed router included)
↓ Each RFS generates resource requirements

The Decomposition Process

When a service order item with an add action is processed, the SOM engine executes the following decomposition workflow:

  1. Retrieve the CFS specification from the Service Catalog (TMF633). The CFS specification defines the service structure, including its characteristics, relationships, and the RFS specifications that compose it.
  2. Validate the service order item characteristics against the CFS specification's required and optional attributes. For example, verify that mandatory characteristics like "Bandwidth" and "Service Address" are provided and conform to allowed values.
  3. Create the CFS instance in the service inventory (SLM) with state "Feasibility". The instance captures the CFS characteristics as provided by the order item.
  4. Decompose into RFS instances: For each RFS specification referenced by the CFS specification, create an RFS instance. Map the CFS characteristics to RFS characteristics as defined by the decomposition rules in the catalog.
    Example mapping: CFS Bandwidth "100Mbps" → RFS Port Profile "100Mbps", RFS QoS Profile "Gold", RFS VPN Profile "Standard".
  5. Create resource requirements: For each RFS instance, determine the resource specifications (from the Resource Catalog TMF634) that are needed. Resource requirements may be concrete (specific device type, port type) or abstract (placeholder that will be resolved during resource allocation).
  6. Generate topology relationships: Define the service topology by establishing service relationships between the CFS and RFS instances, and between RFS instances where dependencies exist. For example, the MPLS VPN RFS "reliesOn" the MPLS Port RFS.
  7. Submit resource requirements to ROM: SOM creates a TMF652 Resource Order containing the resource requirements and submits it to the ROM layer for allocation and activation.
  8. Track state: SOM transitions the CFS instance state through Designed and Reserved as resource allocation progresses, and finally to Active when ROM reports successful activation.

Design pattern: The decomposition rules that define how CFS maps to RFS, and how RFS maps to resource specifications, are stored in the Service Catalog (TMF633) and Resource Catalog (TMF634). This means that service designers can change the decomposition behaviour by updating catalog entries, without modifying the SOM orchestration engine code. This is the catalog-driven design principle applied at the service layer.

Service Topology and Relationships

Modern telecom services are rarely standalone. They form complex topologies with multiple interconnected service instances across different domains. SOM is responsible for managing these relationships and ensuring that the topology is correctly represented in the service inventory.

Common Service Relationship Types

  • reliesOn: The source service depends on the target service being active before it can operate. For example, an MPLS VPN RFS "reliesOn" the MPLS Port RFS being active.
  • connectsTo: The source service connects to the target service, typically over a network link. For example, a CFS "connectsTo" a network termination point.
  • bundledIn: The source service is a component of a larger composite service. For example, a Managed Router CFS is "bundledIn" a Managed MPLS VPN service bundle.
  • covers: The source CFS is covered by the target SLAs or service level specifications.
  • dependsOn: A general dependency relationship, similar to reliesOn but with weaker semantics.
  • connectsToNetwork: The service connects to a specific network resource or domain.

Service Topology Management

SOM maintains a service topology graph that captures the relationships between all CFS and RFS instances for a given customer order. This topology is essential for:

  • Activation ordering: Determining which services must be activated before others (e.g., port must be active before VPN can be configured).
  • Impact analysis: When a service fails or is scheduled for maintenance, determining which other services will be affected.
  • Root cause analysis: When a customer reports a problem with their CFS, tracing through the topology to identify the failing RFS or resource.
  • Change management: Understanding the blast radius of a proposed change to a service instance.

Lifecycle Management in SOM

SOM is responsible for managing the complete lifecycle of service instances, from initial design through active operations to eventual termination. The service lifecycle is closely tied to the commercial order lifecycle but has its own distinct states and transitions.

Service Order Modification

When a customer requests a change to their service (e.g., upgrading from 100Mbps to 200Mbps), the COM layer creates a commercial order with a modify action. SOM receives a corresponding service order item and executes the following:

  1. Retrieve the existing CFS instance from the SLM installed base.
  2. Validate the requested characteristic changes against the CFS specification.
  3. Identify which RFS instances need to be modified (e.g., a speed upgrade affects the Port RFS and QoS RFS, but not the VPN RFS).
  4. Create resource order items for the affected RFS, with the modified characteristics.
  5. Track the modification through to completion, updating the CFS instance state.

Service Disconnection

When a customer cancels a service, COM sends a delete action to SOM. The service disconnection process involves:

  1. Retrieve the CFS instance and all related RFS instances from SLM.
  2. Determine the deactivation ordering: typically, higher-layer services are deactivated before lower-layer services (e.g., VPN before Port).
  3. Create resource orders with delete actions for each RFS instance.
  4. After ROM confirms deactivation, update the CFS and RFS instances to "Terminated" state in SLM.
  5. Notify COM that the service has been decommissioned.

SOM Integration Patterns

SOM is the central integration hub between the commercial and network layers. Its integration landscape includes:

  • COM (Upstream): Receives TMF641 service orders from COM. Sends state change notifications back to COM.
  • Service Catalog (Reference): Reads CFS and RFS specifications to drive decomposition logic.
  • Resource Catalog (Reference): Reads resource specifications to determine resource requirements.
  • SLM / Service Inventory (Sink): Writes service instance data to the SLM installed base (TMF638).
  • ROM (Downstream): Submits TMF652 resource orders to ROM for resource allocation and activation.
  • Domain Orchestrators (Downstream, via ROM): In architectures where SOM directly interacts with domain orchestrators (e.g., SDN controllers), SOM may bypass ROM for certain operations.
  • Assurance Systems (Reference): Service topology and state data from SOM feeds service assurance and monitoring systems.

Key Takeaways

  • SOM is the middle layer in the three-layer order model, responsible for translating commercial requests into service designs and resource requirements.
  • Customer Facing Services (CFS) represent the service as the customer experiences it; Resource Facing Services (RFS) represent the service as the network implements it.
  • TMF641 Service Ordering API defines the standard interface for SOM, including service order business objects, state machines, and notification events.
  • CFS decomposition is the core SOM function, breaking CFS into RFS instances and generating resource requirements that are passed to the ROM layer.
  • The service instance lifecycle spans Feasibility, Designed, Reserved, Active, Suspended, and Terminated states, managed within the SLM installed base.
  • Service topology and relationship management enable activation ordering, impact analysis, root cause tracing, and change management.
  • Decomposition rules are stored in the Service and Resource Catalogs, enabling service designers to change behaviour without modifying orchestration logic.
  • Compensation in SOM must handle partial failures by rolling back service instances and releasing resources in coordination with ROM.
